## 3. 이번 정책의 범위

구현 대상은 **미확정 과거 요청을 그대로 남겨 둔 채, 명시적으로 승인될 후속 배치 한 번을 허용하는 제한된 정책**이다. 과거 비용을 확정하는 reconciliation 기능이나 일반적인 다중 계정 결제 플랫폼은 이번 범위가 아니다.

다음 원칙을 코드로 검증할 수 있어야 한다.

1. 과거 UNCERTAIN, 예약, 소비 ID와 원본 journal은 불변이다. 위험 수용 기록은 무과금 증명, usage 보충 또는 예약 면제가 아니다.
2. 하나의 신뢰된 운영 이력에 과거 v1과 향후 새 프로토콜의 실행을 연결한다. 새 파일을 만드는 것만으로 기존 미해결 이력 검사를 피할 수 없어야 한다.
3. 이번 예외는 지정한 과거 run과 불확정 요청에만 적용하며, 지정할 후속 run 한 번만 허용한다. 미래의 모든 UNCERTAIN을 허용하는 전역 스위치를 만들지 않는다.
4. 후속 실행에 새 OPEN/UNCERTAIN이 생기면 자동 재개, 재시도, 다른 run 생성 또는 다음 배치로 이어지지 않는다. 추가 예외는 이번 정책 밖이다.
5. 기본값은 계속 차단이다. 새 정책, 이력 인수, 정확한 승인 결합이 없으면 키 조회 전에 거부한다. 합성 모드에서도 실제 전송 진입점은 차단한다.

현재 v1/v2의 엄격한 reader와 동결 감사 경로는 보존한다. 새로운 운영 프로토콜 또는 원장 버전이 필요하면 명시적으로 새 버전을 부여한다. 기존 DB marker나 기존 report를 바꿔 새 버전처럼 보이게 하지 않는다.

## 4. 이력 원장과 신뢰 기준

구체적인 모듈 및 테이블 구성은 기존 SQLite와 표준 라이브러리 설계에 맞춰 선택하되 다음 조건을 만족한다. 후속 실행의 권위 원장과 journal을 같은 SQLite 파일의 트랜잭션으로 묶을 수 있으면 그 방식을 우선한다. 두 DB 사이의 부분 성공을 원자적 성공이라고 주장하지 않는다. 별도 파일이 꼭 필요하면 각 crash prefix에서 후속 전송이 차단됨을 입증한다.

### 과거 이력 인수

- 원본 registry 식별자 및 경로, protocol/source, 원본 report hash, journal count/tail, 모든 소비 run/approval ID, 상태, 확인 비용과 미확정 예약을 연결한다.
- 실제 인수 전에 원본 DB의 이력 목록과 제출 report 목록이 일치해야 한다. 알려진 한 run만 골라 다른 행을 누락하는 인수는 거부한다. 관련 probe 계보가 더 발견되면 현재 한도 계산을 그대로 적용하지 않는다.
- 과거 report는 해당 동결 runtime으로 재계산해 검증한다. 새 runtime에서 임의로 옛 스키마를 느슨하게 허용하거나 제출된 `audit=true` 문자열만 신뢰하지 않는다. 검증 결과를 인수 증거로 쓴다면 runtime identity, 입력 hash와 전체 이력 목록을 결합한다.
- 과거 원본은 읽기 전용 참조 또는 검증된 불변 입력으로 유지한다. 새 권위 원장에 등록된 요약도 원본과 다시 대조할 수 있어야 한다.
- 미래 운영 bootstrap은 별도 승인 단계의 작업이다. 이번에는 임시 모의 이력으로 bootstrap 로직과 거부 조건만 검증한다. 실제 권위 원장이나 운영 이력 인수 완료 표시를 생성하지 않는다.

### 기기, 경로, 최신 기준점

- 한 운영 기기와 고정 권위 원장 경로를 승인 결합에 포함한다. 데스크톱 외 기기는 이력 인수와 새 결합 없이는 거부한다. hostname만으로 신뢰 가능한 기기 인증을 구현했다고 주장하지 않는다.
- 원장 identity, imported-history digest, 최신 event sequence/tail과 다음 실행 binding을 결합한다. 파일 누락 시 자동으로 빈 원장을 초기화하거나 fallback하지 않는다.
- 허용된 이력과 소비 ID를 재생성한 빈 원장, stale 사본, 부분 rollback, 잘못된 경로, SQLite sidecar를 무시한 상태 오판을 검사한다.
- 모든 파일과 승인 기준점을 함께 과거로 되돌린 경우까지 로컬 hash만으로 탐지할 수는 없다. 신뢰하는 최신 기준점과 운영자의 다른 기기 실행 금지 전제를 문서화한다. 이를 해결한다며 서버나 분산 합의 시스템을 추가하지 않는다.
- 기존 동결 runtime은 감사용이다. 옛 실행 프로그램으로 별도 실행하는 행위까지 새 로컬 코드가 원격 통제한다고 표현하지 않는다. 승인된 운영 진입점과 보존용 감사 진입점을 명확히 구분한다.

## 5. 승인 결합과 단일 실행

실제 사용자 승인 파일은 생성하지 않는다. 코드가 향후 검사할 계약과 명시적인 테스트 fixture만 구현한다. 오프라인 정책 제안 파일은 사람 승인으로 읽을 수 없는 별도 스키마여야 한다.

정책 결합에는 최소한 다음 내용을 넣는다.

- 정책 버전과 정확히 허용할 과거 run/request/body 및 원본 이력 digest.
- 과거 확인 비용, 미확정 노출, 비용이 여전히 미확정이라는 사실.
- 후속 run ID와 일회성 risk acceptance ID, paid approval ID 및 각 소비 기록. 한 문서로 묶거나 분리할 수 있으나 이중 의미를 명시적으로 결합한다.
- 새 source, corpus, schedule, protocol, plan, endpoint 및 전체 후보 예산.
- 운영 기기 식별값과 권위 원장 경로/identity, 최신 이력 기준점.
- 승인자 진술, 대상 범위, 유효 시작과 만료 시각, 한 번만 사용 가능하다는 조건.

새 후속 run의 기존 이력 확인, 승인 검증, 중복 ID 확인, 누적 예산 확인 및 영속 claim은 키 조회 전에 완료돼야 한다. TOCTOU가 생기지 않도록 검증과 claim을 동일한 직렬화 경계에서 처리한다. 실행 전체의 단일 writer 조건과 각 요청의 영속 예약을 유지한다. 프로세스 중단이나 저장 실패 시 이미 소비한 ID를 다시 미소비로 돌리지 않는다.

기존 정상 run 경로에 선택적인 검사만 붙여 새 경로의 guard를 생략할 수 있게 하지 않는다. 현재 코드의 실제 probe 실행 진입점이 새 계보 정책을 우회해 빈 registry로 실행할 수 없는지 확인한다. 테스트용 recording 경로의 유연성을 실제 HTTP 경로에 그대로 노출하지 않는다. 기존 paid-life 실험의 별도 계약은 무관하게 변경하지 않는다.

## 6. 오프라인 구현 후보 예산

원래 72슬롯과 요청별 예약을 줄이지 않고 코드가 허용하는 최대 usage의 72회 trace를 수용하는 후보를 구현한다. **아래 수치는 실제 지출 승인이나 예상 소비량이 아니다.** 최종 실행 승인안에서 사용자가 확인할 값이다.

| 요청 수 | 72 |
| 재시도 | 0 |
| 요청당 출력 한도 | 8,192 |

누적 한도 범위는 이번 probe 계보다. 별도 생활 실험 비용을 포함한 프로젝트 전체 비용으로 표시하지 않는다. 인수 과정에서 추가 probe 이력을 발견하면 위 합계가 더 이상 전체 이력을 포괄하지 않으므로 중단해 후보를 재계산한다.

고정 단가는 기존 계획의 입력 750, cached 75, 출력 4,500 nano-USD/token을 사용한다. 72 × (400,000 × 750 + 8,192 × 4,500) = 24,254,208,000 nano-USD다. 추론 토큰을 출력 토큰에 다시 더하지 않는다. 이 산술은 고정 신원, 유효 usage 및 단가 조건 아래의 코드 계산이며 외부 청구의 무조건 상한이 아니다.

기존 US$1.00 계획을 조용히 새 값으로 바꾸지 않는다. 후보는 별도 명시적 plan 버전으로 선택하고 그 값 전체를 승인 결합에 넣는다. 불명확한 임의 override나 자동 증액을 허용하지 않는다. 기존 v1/v2 보고서 감사는 당시 계획으로 유지한다.

새 run에 대해서도 매 요청마다 요청 수, 입력 예약, 출력 예약, 비용 예약, 미해결 예약을 함께 검사한다. 계보 전체는 과거 확인 비용 + 과거 미확정 노출 + 새 run 확인 비용 + 새 run의 현재 예약으로 재계산할 수 있어야 한다. batch 전체 예산을 별도 capacity hold로 기록한다면 같은 돈을 요청 예약과 중복 합산하거나 반대로 누락하지 않도록 승인 용량과 관측 회계를 구분한다.

과거와 새 run의 total cost를 구분한다. 새 run이 FINISHED여도 과거가 미확정이면 계보 전체 실제 비용은 계속 null이다. 알려진 비용 합계와 조건부 노출 합계를 별도 필드로 표시한다. 새 run도 UNCERTAIN이면 그 예약을 과거 예약과 별도로 유지하고 후속 claim을 차단한다.

## 7. 필수 오프라인 검증

실제 socket/DNS/HTTPS 및 credential 진입점을 차단한다. 가짜 승인, 가짜 키와 fake HTTP는 테스트 fixture임을 파일과 보고서에 명시한다. 실제 승인자의 승인을 받았다고 표시하지 않는다.

| 검증 범위 | 필요한 결과 |
| --- | --- |
| 정책 또는 유효 승인 없음 | 키 조회 및 HTTP 0회, claim 거부 |
| 합성 승인을 실제 경로에 대입 | 실제 진입 거부 |
| 이력/원장 누락, 빈 DB, 잘못된 경로/기기 | 자동 생성이나 fallback 없이 거부 |
| 원본 행 누락, 다른 report, hash/tail/순서/소비 ID 변조 | 이력 인수 또는 실행 전 거부 |
| 기존 run/approval 및 새 risk acceptance ID 재사용 | 재프로세스에서도 거부 |
| 승인 만료, 다른 source/plan/예산/대상 불확정 요청 | 키 조회 전 거부 |
| 동시에 두 프로세스가 같은 권위 원장에 claim | 한 실행만 claim, 패자는 키/HTTP 0회 |
| 승인 직후 원본/최신 이력 변경 | stale 결합 거부, 원래 승인으로 진행 금지 |
| claim/예약/전송 기록/응답/정산 저장 실패 | 마지막 확정 prefix 보존, 후속 전송 차단, 재사용 금지 |
| commit 직후 호출자에게 예외 | 자동 rollback 보상이나 재실행 없이 보수적 차단 |
| 과거 비용 0 처리, 예약 누락, 이중 차감 또는 이중 합산 | 재계산 불일치 거부 |
| 새 run 성공 | 과거 UNCERTAIN 및 예약은 유지, 새 비용만 확정, 계보 총비용 null |
| 새 run의 1/17/72번째 전송 불확정 | 해당 위치에서 중단, 새 예약도 유지, 엔진 미전달, 자동 추가 batch 없음 |
| 늦은 완전 응답/부분 수신/PE-R1 framing | 기존 분류 및 usage 회수와 엔진 차단 유지 |
| 요청 72개 및 fixtures | 본문, 순서, effort와 평가 입력 불변 |

비용과 token gate는 다음을 포함해 실제 후보 Ledger/runner로 검증한다. 별도 산술 함수의 성공만으로 구현 검증을 대체하지 않는다.

- 슬롯당 입력 400,000 및 출력 8,192의 최대치 72회가 후보 plan에서 admission을 통과하며 73번째는 거부된다.
- 입력, 출력, 새 run 비용 및 계보 누적 한도의 정확한 경계와 1 초과를 각각 거부한다.
- 첫 요청부터 과거 확인 비용과 미확정 예약이 누적 계산에 포함된다.
- 작은 usage와 cached usage에서는 실제 알려진 비용을 올바르게 계산하지만 알 수 없는 usage를 0으로 만들지 않는다.
- 원래 US$1.00/500,000 계획은 기존 결과를 유지하며 새 후보로 암묵 변환되지 않는다.

전체 72슬롯 정상 모의 실행과 1/17/72번째 실패, claim 저장 중단, 중복 프로세스 시도의 근거를 보존한다. 새 프로세스의 data-only 감사에서 원장, 원본 이력 결합, journal, 회계와 engine 결과를 재계산한다. 네트워크 없이 검사하는 순수 감사와 운영 기기에서의 실행 자격 검사를 분리하고, portable audit 통과가 현재 writer 부재나 실행 승인을 뜻하지 않게 한다.

기존 실제 v1 report는 a362 동결 runtime에서 계속 감사한다. 새 소스로 과거 report를 다시 만들지 않는다. 이번 변경 전 v2 runtime도 source 912eb145로 필요한 감사 범위만 보존해 v2 보고서의 검증 경로가 끊기지 않게 한다. 키, 실제 승인 원문이나 운영 DB를 동결 source 폴더에 섞지 않는다.

관련 pytest, Ruff check, format, strict mypy와 diff 검사를 수행한다. 변경된 승인/회계 진입점의 관련 회귀를 포함한다. 전체 회귀가 계약상 필요하면 그 근거를 명시하고 수행하며, 시간 절약을 위해 필요한 검증을 생략하지 않는다. F1 재현만을 위한 반복 조사는 하지 않는다.

## 8. 완료 자료와 종료점

완료 보고서에는 구현 완료, 모의 검증 완료, 독립 검토 필요, 운영 인수 및 실제 승인 미완료를 구분한다. 예상 source identity를 임의로 먼저 쓰지 말고 구현 후 실제 값을 계산한다.

제출물:

1. 변경 전후 source, 변경 파일 목록, 기존 72개 요청/fixtures 불변 증거.
2. 정책 및 plan 계약, 이력 인수와 권위 원장 구조, 승인 결합 및 crash 상태 전이 설명.
3. 실제 테스트 명령, 버전, stdout/stderr, JUnit, 정적 검사 결과.
4. 정상 72슬롯 및 실패/저장 중단/경합 모의 근거와 새 프로세스 감사.
5. 기존 실제 자료, 운영 registry, 승인, Git refs 및 지정 범위 밖 작업의 보존 대조.
6. 현재 source에서 만들 수 있는 비활성 정책 후보의 스키마와 예산 요약. 실제 run/approval 발급이나 운영 인수는 하지 않는다.
7. 독립 검토 ZIP: 이번 before/after, patch, 계약, 테스트 및 감사 근거, manifest와 재현 절차. 이번 912eb145 기준 검토본에 적용해 재구성할 수 있게 한다. 운영 DB와 키 및 사람 승인 원문을 포함하지 않는다.

기존 파일을 덮어쓰는 전체 백업이나 무관한 드라이브 전체 해시를 반복하지 않는다. 패키지 안에 필요한 변경 및 근거만 넣는다. 파일명과 경로를 완료 보고서에 명시한다.

**여기서 정지한다.** 다음은 새 정책 구현의 독립 검토다. 이번 작업에서 실제 운영 이력 bootstrap, 운영 DB 쓰기, 키/계정 접근, 실제 API 호출, 사람 승인 생성, 재시도/재개, commit/push/merge는 수행하지 않는다. 실제 유료 실행안은 이 검토를 통과한 소스와 사용자에게 제시할 정확한 금액을 기준으로 별도 준비한다.
